---
name: fast-track-ai-implement
description: Implement a track task by task with validation, review, and final gate. Use when spec and tasks are approved and the user says "implement this", "build the track", or "execute the plan". Never run before spec approval.
---

1. Read `fast-track-ai/tracks/NNN-slug/intent.md`, `spec.md`, and `tasks.md` in the target repo. Require `intent.md` and frontmatter `status: approved` in `spec.md` and `tasks.md`. Intent `status: active` is not required. A leftover `spec/` directory is historical and is never the authority. Do not require `plan.md`.
2. Respect boundaries. Touch ONLY files listed in the spec Files and each task's Files. Auxiliary outputs go under `assets/`, never loose at the track root. Never implement items in `out_of_scope`. Never question `assumed_state`. If a task needs an unlisted file or an out-of-scope item becomes necessary, stop and ask before touching anything. When the user makes a qualifying decision during implementation, file `fast-track-ai/decisions/<NNN-slug>.md` from `../fast-track-ai-spec/assets/decisions.md` (owner copy) without a separate request. Status is `accepted | superseded` only.
3. Create ALL tasks upfront in TodoWrite from the task list, with phase tags.
4. Use subagents when possible. Independent tasks go to parallel subagents, one task per agent. Dependent tasks run in sequence. Never parallelize edits to the same file. The main agent owns integration, shared files, and final validation.
5. Validate before marking complete. Run each task's Validate command. Run typechecking regularly, single test files regularly, full suite once at the end. Never mark a task complete on an untested change.
6. After all tasks, run `../fast-track-ai-spec/scripts/fast-track-ai-gate.sh --track NNN-slug --root <target>` (owner copy, referenced by package-relative path), then a package-owned review adapted from `fast-track-ai/refs/code-review-skill` (pointer; do not vendor the upstream tree). Principles: catch bugs and edge cases; keep the change maintainable; comment on the code, not the person; skip formatting that a linter owns. Phases: (1) context from intent, spec, and the diff; (2) high-level fit to the spec Files and Out of scope; (3) line-by-line on listed files for correctness, security, and invented answers or unlisted edits; (4) summary plus a decision. Severity: `[blocking]` must fix, `[important]` should fix, `[nit]` optional, `[suggestion]` alternative, `[praise]` keep. Report diff stat, deviations from the spec, and new patterns found.
7. Update task checkboxes, regenerate `fast-track-ai/INDEX.md` with `../fast-track-ai-init/scripts/fast-track-ai-index.sh <target>` (owner copy), and stop for user review. Ask for an explicit ship. Checkboxes and a green gate never ship by themselves. Never write `shipped` before the ask. After the maintainer approves the ship, set intent `status: shipped` and regenerate `INDEX.md` again.
