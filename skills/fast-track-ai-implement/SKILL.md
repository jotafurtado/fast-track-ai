---
name: fast-track-ai-implement
description: Implement a track task by task using parallelism groups, with validation, review, and final gate. Chains to ship on user continuation. Never run before spec approval.
---

1. Read `fast-track-ai/tracks/NNN-slug/intent.md`, `spec.md`, and `tasks.md` in the target repo. Require `intent.md` and frontmatter `status: approved` in `spec.md` and `tasks.md`. Intent status may stay `draft`. A leftover `spec/` directory is historical and is never the authority. Do not require `plan.md`.
2. Respect boundaries. Touch ONLY files listed in the spec Files and each task's Files. Auxiliary outputs go under `assets/`, never loose at the track root. Never implement items in `out_of_scope`. Never question `assumed_state`. If a task needs an unlisted file or an out-of-scope item becomes necessary, stop and ask before touching anything. When the user makes a qualifying decision during implementation, file `fast-track-ai/decisions/<NNN-slug>.md` from `../fast-track-ai-spec/assets/decisions.md` (owner copy), cite supporting evidence when available, and use only `accepted | superseded`. If that decision conflicts with or materially changes approved `spec.md` or `tasks.md`, stop implementation, reconcile the ADR plus both planning artifacts, and require renewed explicit approval before resuming. If it does not materially change approved scope or design, record it and continue. Do not create an ADR for a local, easily reversible, or obvious choice.
3. Create ALL tasks upfront in TodoWrite from the task list, with phase tags.
4. Resolve parallelism groups from `tasks.md`. Read `## Group <name>` headers and `(depends: <group>)` annotations. Launch groups in dependency order; tasks within one group run in parallel subagents, one task per agent. Dependent groups run in sequence. Never parallelize edits to the same file. Use subagents when possible. Request an execution-class agent from the harness for task subagents and reserve the session model for planning, integration, shared files, review, and final validation. Do not hardcode model names or provider-specific identifiers. The main agent owns integration, shared files, and final validation.
5. Validate before marking complete. Run each task's Validate command. Run typechecking regularly, single test files regularly, full suite once at the end. Never mark a task complete on an untested change.
6. After all tasks, run `../fast-track-ai-spec/scripts/fast-track-ai-gate.sh --track NNN-slug --root <target>` (owner copy, referenced by package-relative path), then a package-owned review adapted from `fast-track-ai/refs/code-review-skill` (pointer; do not vendor the upstream tree). Principles: catch bugs and edge cases; keep the change maintainable; comment on the code, not the person; skip formatting that a linter owns. Phases: (1) context from intent, spec, and the diff; (2) high-level fit to the spec Files and Out of scope; (3) line-by-line on listed files for correctness, security, and invented answers or unlisted edits; (4) summary plus a decision. Severity: `[blocking]` must fix, `[important]` should fix, `[nit]` optional, `[suggestion]` alternative.
7. Present a post-implementation summary. Format:
   - Four short bullets: completed tasks, test results, review outcome, gate result.
   - Next-step line: `. para ship (marca a track como concluida)`.
   Update task checkboxes, regenerate `fast-track-ai/INDEX.md` with `../fast-track-ai-init/scripts/fast-track-ai-index.sh <target>` (owner copy), and stop for user review. Checkboxes and a green gate never ship by themselves. Never write `shipped` before the ask.
8. Wait for user input. If the user replies `.` or an affirmative synonym ("sim", "pode continuar", "yes", "continue"), set intent `status: shipped` and regenerate `INDEX.md` again. Any other input is processed as an instruction to fix or revise before shipping.
