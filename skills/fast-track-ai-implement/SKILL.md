---
name: fast-track-ai-implement
description: Implement a track task by task using parallelism groups, with validation, review, and final gate. Chains to ship on user continuation. Never run before spec approval.
---

1. Read `fast-track-ai/tracks/NNN-slug/intent.md`, `spec.md`, and `tasks.md` in the target repo. Require `intent.md` and frontmatter `status: approved` in `spec.md` and `tasks.md`. Intent status may stay `draft`. On resume, treat each `- [x]` task as already validated and continue from the first open task in dependency order; do not rerun a checked task's Validate unless a later change touches that task's Files, in which case rerun that task's Validate before offering ship.
2. Respect boundaries. Product edits are restricted to files listed in the spec Files and each task's Files; stop and ask before touching any other product file. Never implement items in `out_of_scope`. Treat the intent's `Assumed state` by provenance: take each `Stated by the user` fact as given, and verify each `Unverified assumptions` entry before a task depends on it. When a stated fact or an assumption proves false, record the divergence in the track's `assets/`, then stop and report it to the user before changing the approach; do not adapt the solution on your own. Method-administration files change only through named transitions: task checkboxes in `tasks.md`, files under the track's `assets/`, `fast-track-ai/INDEX.md` through the owner index script, intent `status: shipped` after the ship confirmation, new ADRs under `fast-track-ai/decisions/`, and returning `spec.md` and `tasks.md` to `draft` on a material change. When the user makes a qualifying decision during implementation, file `fast-track-ai/decisions/<NNN-slug>.md` from `../fast-track-ai-spec/assets/decisions.md` (owner copy), cite supporting evidence when available, and use only `accepted | superseded`. If that decision conflicts with or materially changes approved `spec.md` or `tasks.md`, stop implementation, return both `spec.md` and `tasks.md` to `draft`, reconcile the ADR plus both planning artifacts, present a new spec summary ending with `. para implementar`, and require renewed explicit approval before resuming. If it does not materially change approved scope or design, record it and continue. Do not create an ADR for a local, easily reversible, or obvious choice.
3. Create all tasks upfront in the task tracker the harness provides, if any, with phase tags.
4. Resolve parallelism groups from `tasks.md`. Read `## Group <name>` headers and `(depends: <group>)` annotations. Launch groups in dependency order. Tasks within one group may run in parallel; each delegated task gets its own subagent; when the harness cannot run subagents, run the tasks of each group sequentially, preserving group dependency order. Dependent groups run in sequence. A dependent group starts only after every task of each group it depends on has passed Validate and is checked `- [x]` in `tasks.md`; until then, do not create, edit, or delete any file listed in a dependent task's Files, including to stage work or to collect evidence. When a prerequisite task's Validate fails, stop before every dependent group and report the failure. Never parallelize edits to the same file. Delegate proportionally: when the harness offers subagents, delegate a task to a subagent only when it warrants its own context, that is more than one file or a Validate that runs beyond a single quick check; run a trivial task directly in the main agent. Request an execution-class agent from the harness for task subagents and reserve the session model for planning, integration, shared files, review, and final validation. Do not hardcode model names or provider-specific identifiers. The main agent owns integration, shared files, and final validation. Do not run project-wide checks, such as a full test suite, a build, or a typechecker, while subagents of the current group are still editing; defer those global checks until every task in the group has returned.
5. Validate before marking complete. Run each open task's Validate command and the checks the target project actually provides (such as existing test suites or typecheckers); do not invent or assume commands for tools the project does not configure. Select task-scoped project checks by the resume rule in step 1, including scripts used for final project validation: a task's Validate remains task-scoped even when it is the project's only check script. Set the task's checkbox to `- [x]` in `tasks.md` as soon as its Validate passes, before starting the next dependent group. Never mark a task complete on an untested change, and keep the checkbox open if Validate fails.
6. Demonstrate acceptance before ship. After all tasks pass Validate, write `fast-track-ai/tracks/NNN-slug/assets/acceptance.md`. Structure it as a Markdown table with the columns `Criterion | Check | Observed | Result`. Include one row for the spec Outcome and one row per phase `Accept:` line. Execute each check against the final state of the change and record the observed output. Set `Result` to `met` or `pending`. Every row must be `met` before ship is offered.
7. Run the completion gate and review. With all tasks marked `[x]`, run `../fast-track-ai-spec/scripts/fast-track-ai-gate.sh --track NNN-slug --root <target>` (owner copy, referenced by package-relative path), then conduct a package-owned review. `fast-track-ai/refs/code-review-skill` names only the provenance of the approach; the full review procedure is the text that follows in this skill, and the consuming project does not need that ref, so the review runs the same way whether or not it exists. Principles: catch bugs and edge cases; keep the change maintainable; comment on the code, not the person; skip formatting that a linter owns. Phases: (1) context from intent, spec, and the diff; (2) high-level fit to the spec Files and Out of scope; (3) line-by-line on listed files for correctness, security, and invented answers or unlisted edits; (4) summary plus a decision. Severity: `[blocking]` must fix, `[important]` should fix, `[nit]` optional, `[suggestion]` alternative. If there is any `[blocking]` finding, fix it, rerun the Validate commands of affected tasks and acceptance checks of affected phases, update `Observed` and `Result` for the affected rows in `assets/acceptance.md`, re-run the completion gate, and repeat the review until no `[blocking]` finding remains. Fix each `[important]` finding or list it as open.
8. Present a post-implementation summary. Format:
   - Four short bullets: completed tasks, acceptance `N/M met (assets/acceptance.md)`, review outcome, gate result.
   - Next-step line: `. para ship (marca a track como concluida)`.
   Regenerate `fast-track-ai/INDEX.md` with `../fast-track-ai-init/scripts/fast-track-ai-index.sh <target>` (owner copy), and stop for user review. Show the ship next-step line only when every acceptance row is `met` and no `[blocking]` finding remains; if any row is `pending`, report it and continue fixing or ask how to proceed. Checkboxes and a green gate never ship by themselves. Never write `shipped` before the ask.
9. Wait for user input. If the user replies `.` or an affirmative synonym ("sim", "pode continuar", "yes", "continue"), set intent `status: shipped` and regenerate `INDEX.md` again. Any other input is processed as an instruction to fix or revise before shipping.

Path resolution: `./` paths and `../fast-track-ai-*` sibling paths resolve from this skill's installed directory, and `fast-track-ai/` paths resolve from the target repository root.
