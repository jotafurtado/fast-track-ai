---
name: fast-track-ai-intent
description: Draft the intent of a new request from the conversation, with interactive clarification and autonomous artifact generation. Chains to spec on user continuation. Do not write spec.md. Intent approval is not required before spec.md. Never implement without approved spec.md and tasks.md.
---

1. Listen to the request in the user's own words. Do not write `spec.md`. Do not implement.
2. Classify the request as a change, research-only, or assessment-only before allocating a number. If the request is too vague or ambiguous to classify, ask the user using the host interactive ask pattern (capped at three focused questions in that pass).
3. If the request is purely investigative ("pesquise", "investigue") or evaluative ("avalie", "audite") and does not describe a desired state change in the system, route the request to `fast-track-ai-research` or `fast-track-ai-assess` as a direct call. Create no track directory and no `intent.md`. Stop there.
4. For a change request, find the next free number under `fast-track-ai/tracks/` in the target repo. Format `NNN-slug`, kebab-case slug of what was asked.
5. If the change request is too vague to draft an intent, ask the user using the host interactive ask pattern. Cap: three focused questions in that pass. Each question must explain why it matters and which decision it unlocks. Write answers into the intent body, not as disconnected conversation. Leave leftovers under `Open questions`. Do not run an unbounded grill. If already decided, skip the questions.
6. Check for autonomous artifact triggers before drafting. Inform the user in one sentence before each invocation; do not ask permission. Invoke research and assessment triggers as an auxiliary step for change requests only:
   - **Research**: the user mentions a technology, API, pattern, or external fact you cannot confirm with confidence. Well-known technologies you already know do not trigger research. Invoke `fast-track-ai-research` as an auxiliary step and cite the research slug in `research:`.
   - **Ref**: the user supplies a URL, document, or external code snippet that materially grounds the intent. Capture it at `fast-track-ai/refs/<slug>.md` from `./assets/ref.md` and cite the slug in `refs:`. Keep the entire resulting ref file, including frontmatter and notes, at or below 500 KB. Use `inline` only for redistributable normalized text that fits within that whole-file limit; use `pointer` for large, binary, stable-upstream, restricted, or unknown-license content. Record `content_license`, hash captured source bytes rather than a locator, use an immutable `pin` when available or `retrieved_at` otherwise, and compare the hash with existing refs before writing so duplicate content reuses the existing slug. Source identity is immutable: changed bytes require a new ref. If the source remains inaccessible after one direct request, create no ref or synthetic hash; record the missing basis under `Open questions` or `Assumed state`.
   - **ADR**: an answer to a clarifying question meets the qualifying criteria (durable, costly to reverse, surprising without context, or resolves a meaningful trade-off). Create the next numbered `fast-track-ai/decisions/<NNN-slug>.md` from `../fast-track-ai-spec/assets/decisions.md` and cite its slug in the intent `decisions:` list. Cite supporting refs, research, or assessments when available. Do not create an ADR for a local, easily reversible, or obvious implementation choice.
   - **Assessment**: the intended change depends on the current condition of a system you can inspect. Run the `fast-track-ai-assess` skill as an auxiliary step and cite the assessment slug in `assessments:`.
7. Draft `fast-track-ai/tracks/NNN-slug/intent.md` from `./assets/intent.md` bundled in this skill. Reference external research by slug in `research:`. Cite inward evaluations from `fast-track-ai/assessments/` in `assessments:`, never in `research:`. Cite Architecture Decision Records from `fast-track-ai/decisions/` in `decisions:`.
8. Regenerate `fast-track-ai/INDEX.md` with `../fast-track-ai-init/scripts/fast-track-ai-index.sh <target>` using the owner copy and report any validation error instead of presenting the summary as complete.
9. Present a post-phase summary. Format:
   - Four short bullets: problem, proposed outcome, scope, constraints.
   - List of generated artifacts (research, refs, ADRs, assessments), if any.
   - Track location: `fast-track-ai/tracks/NNN-slug/`.
   - Next-step line: `. para continuar com a spec`.
   Do not report draft status as failure. Do not present an approval gate.
10. Wait for user input. If the user replies `.` or an affirmative synonym ("sim", "pode continuar", "yes", "continue"), invoke the `fast-track-ai-spec` skill for the same track. Any other input is processed as an instruction to revise the intent before proceeding; after revision, regenerate `fast-track-ai/INDEX.md` with `../fast-track-ai-init/scripts/fast-track-ai-index.sh <target>`; report any validation error instead of presenting the summary as complete, otherwise present the summary again.
11. When the maintainer abandons a track, set that intent `status: dropped` and regenerate `fast-track-ai/INDEX.md` with `../fast-track-ai-init/scripts/fast-track-ai-index.sh <target>`. Implementation is not required. When the maintainer replaces a track, set `status: superseded` only after they name `superseded_by`, and regenerate `fast-track-ai/INDEX.md` with `../fast-track-ai-init/scripts/fast-track-ai-index.sh <target>`. Do not invent `superseded_by`.
